# 보스 레이드 대규모 몬스터 최적화

보스 레이드의 드래곤은 체력이 50% 미만이 되면 포효하며 졸개(버그)를 소환합니다. 데이터상 소환 수는 10마리입니다. 부하를 키우려고 개발용 콘솔 변수 `pd.Monster.PhaseSummonCountOverride 200`으로 200마리를 불러 측정했습니다.

목표는 세 가지입니다.

- 전용 서버가 30Hz 틱 예산(33.3 ms)을 지킨다.
- 소환 순간 서버가 멈추지 않는다.
- 클라이언트 프레임을 60 FPS 근처로 유지한다.

## 결과 요약

| 지표 | 기준선 | 최종 |
| --- | --- | --- |
| 서버: 소환 직후 5초의 최대 프레임 | 396.9 ms | 26.9 ms |
| 서버: 소환 뒤 교전 20초 평균 / p95 | 36.4 / 40.7 ms | 18.2 / 21.7 ms |
| 서버: 30Hz 예산(33.3 ms)을 넘은 프레임 | 539 / 551 | 0 / 600 |
| 서버: 클라이언트 1명에게 보내는 양 | 43.4 KB/s | 24.7 KB/s |
| 서버: 졸개 일제 사망 뒤 10초 평균 / 예산 초과 | 23.1 ms / 6프레임 | 5.9 ms / 1프레임 |
| 클라이언트(1280x720): 교전 평균 / p95 | 22.6 / 25.7 ms (44 FPS) | 13.9 / 16.7 ms (72 FPS) |

- 서버 최종값은 3회, 클라이언트 최종값은 2회 측정의 중앙값입니다.
- 클라이언트 기준선은 서버 최적화를 끝낸 뒤에 쟀습니다. 그래서 서버 쪽 변경(복제 빈도 등)의 효과는 클라이언트 표에 들어 있지 않습니다.

## 측정 방법

### 시나리오

[`Scripts/RunPerfBenchmark.ps1`](../Scripts/RunPerfBenchmark.ps1)이 GameLift 없이 로컬 전용 서버(`LV_Colosseum?BossRaid=1`)와 클라이언트 하나를 띄웁니다. 둘 다 `-BossRaidBenchmark`로 실행되어 [`UBossRaidBenchmarkSubsystem`](../Source/LabProject/AI/Monster/BossRaidBenchmarkSubsystem.h)이 측정합니다. 이 서브시스템은 Shipping 빌드에서는 만들어지지 않습니다.

1. 서버가 첫 플레이어를 드래곤 정면에 세우고 무적 태그를 붙입니다. 피해 판정은 그대로 돌기 때문에 졸개가 계속 쫓고 때리는 가장 무거운 상황이 유지됩니다.
2. 10초 기다린 뒤 다음 구간을 잽니다.
   - **소환 전:** 5초
   - **소환 직후:** 5초. 체력과 관계없이 페이즈 소환을 겁니다.
   - **소환 뒤 교전:** 20초
   - **일제 사망:** 10초. 범위 공격 상황을 흉내 내 졸개 전원에게 실제 피해 효과를 적용합니다.
3. 구간마다 `BENCH` 로그를 남기고 서버를 끝냅니다. 스크립트는 로그를 표로 보여 주고 `results.json`으로 남깁니다.

```powershell
# 서버만 (클라이언트는 그리지 않음)
powershell -ExecutionPolicy Bypass -File Scripts\RunPerfBenchmark.ps1 -EngineRoot C:\UE\UE_5.8
# 클라이언트도 그리며 측정
powershell -ExecutionPolicy Bypass -File Scripts\RunPerfBenchmark.ps1 -EngineRoot C:\UE\UE_5.8 -RenderClient
# Unreal Insights 트레이스(Server.utrace, Client.utrace)도 남김
powershell -ExecutionPolicy Bypass -File Scripts\RunPerfBenchmark.ps1 -EngineRoot C:\UE\UE_5.8 -RenderClient -Trace
```

### 지표

**서버 프레임 시간**은 게임 스레드가 한 프레임에 실제로 일한 시간입니다.

- 전용 서버는 30Hz에 맞추려고 매 프레임 쉬기 때문에, 단순한 프레임 간격은 늘 33 ms로 나옵니다.
- 그래서 월드 틱 시작 간격에서 쉰 시간(`FApp::GetIdleTime`)을 뺐습니다. 월드 틱 밖의 가비지 컬렉션과 액터 정리도 이 값에 들어갑니다.
- 30Hz 예산을 넘은 프레임 수와, 넘은 시간의 합(그만큼 시뮬레이션이 밀린 시간)을 함께 남깁니다.

**클라이언트 프레임 시간**은 프레임 제한과 수직 동기를 끄고 잰 프레임 간격입니다. `stat unit`과 같은 게임 스레드, 렌더 스레드, GPU 시간도 같이 남겨 병목을 가립니다.

**`targeting`**은 플레이어를 표적으로 잡은 몬스터 수입니다. 최적화가 AI를 망가뜨리지 않았는지 확인하려고 남깁니다. 이 지표를 처음 넣었을 때 32마리였고, 최종 측정에서도 33~40마리가 플레이어를 쫓았습니다. 나머지는 시야(10 m) 밖에서 배회합니다.

### 환경과 오차

- **실행 환경:** 같은 PC에서 에디터 실행 파일을 전용 서버(`-server`)와 클라이언트(`-game`)로 함께 띄웠습니다.
- **배경 부하:** 측정하지 않을 때도 다른 프로그램이 CPU를 40% 정도 쓰고 있었습니다. 그래서 같은 코드도 실행마다 평균이 2~3 ms씩 달랐습니다.
- **수치를 읽는 법:** 단계별 표는 한 번씩 잰 값이라 작은 차이는 오차 안에 있습니다. 최종값은 여러 번 잰 중앙값입니다.

병목은 `-Trace`로 남긴 트레이스를 Unreal Insights로 열어 찾았습니다. 측정 구간은 트레이스 영역(region)으로 표시되므로 다음처럼 구간별 통계를 뽑을 수 있습니다.

```text
UnrealInsights.exe -OpenTraceFile=<Server.utrace> -AutoQuit -NoUI -ExecOnAnalysisCompleteCmd=@=<rsp>
# rsp 내용
TimingInsights.ExportTimerStatistics <out>/stats_{region}.csv -threads=GameThread -region=*Summon
```

## 무엇을 바꿨나

### 1. 서버 애니메이션 정리

**문제:** 기준선 트레이스에서 교전 중 프레임 약 38 ms 가운데 19 ms가 몬스터 메시 Tick이었습니다.

- 그중 6.6 ms는 버그 애님 그래프의 RigidBody 노드(더듬이 같은 장식의 물리 흔들림)였고, 노드마다 Chaos 시뮬레이션을 따로 돌렸습니다.
- 소환 순간에는 이 노드의 초기화만 200마리에 24 ms가 들었습니다.

**변경:**

- **전용 서버의 RigidBody 노드 끄기:** 화면이 없으니 이 노드는 서버에 필요 없습니다. 메시가 등록되며 애니메이션을 초기화하기 전에 끕니다(`ACharacterBase::PreRegisterAllComponents`).
- **애니메이션을 몇 프레임에 한 번만 갱신:** 서버는 피격 판정용 자세와 노티파이만 쓰므로 졸개는 4프레임에 한 번 갱신합니다. 엔진의 갱신 주기 최적화(URO)가 그리지 않는 메시를 `BaseNonRenderedUpdateRate` 프레임마다 갱신하는 것을 이용합니다(`ServerAnimationUpdateInterval`).
  - 몬스터마다 갱신 프레임이 엇갈려 한 프레임에 몰리지 않습니다.
  - 드래곤은 머리 뼈에 붙인 공격 판정이 빠르게 움직이므로 1(매 프레임)로 둡니다.

**효과:** 교전 평균 36.4 → 25.9 ms, 예산 초과 539 → 17프레임.

### 2. 배회 이동이 매 Tick 경로를 다시 찾던 문제

**문제:** 트레이스에서 버그가 프레임마다 165번씩 경로를 처음부터 다시 찾고 있었습니다.

- `STree_Bug`의 배회 상태("Move To")와 복귀 상태("Return to Spawn Location")는 엔진 MoveTo 태스크에 고정 목적지를 넘깁니다.
- 그런데 두 상태 모두 "목적지 추적"이 켜져 있고 허용 거리는 0이었습니다.
- 엔진은 내비메시에 투영한 목적지와 원래 좌표가 몇 cm만 달라도 목적지가 움직였다고 보고 매 Tick 다시 이동을 겁니다.

**변경:** 목적지가 바뀌지 않는 두 상태의 목적지 추적을 껐습니다. 플레이어를 쫓는 상태는 대상 액터를 넘기므로 경로 추종 컴포넌트가 따로 추적합니다.

### 3. 소환을 프레임 예산으로 나눔

**문제:** 소환 프레임(397 ms)을 쪼개 보니 다음 비용이 한 프레임에 몰려 있었습니다.

- 버그 200마리와 AI 컨트롤러 200개의 생성
- 컴포넌트 등록과 물리 바디 생성
- BeginPlay(200마리에 68 ms)

**변경:** 졸개를 한 프레임에 예산 시간(`pd.Monster.SummonSpawnBudgetMs`, 기본 4 ms)만큼만 만들고, 남은 졸개는 다음 프레임으로 넘깁니다.

- 200마리가 약 2초 동안 나뉘어 나오는데, 이는 드래곤이 포효하는 시간과 비슷합니다. 그래서 포효하는 동안 버그가 쏟아져 나오는 연출이 됩니다.
- 생성 비용 자체는 그대로지만 프레임마다 나눠 갖습니다.
- 미리 만들어 두는 풀링은 이것으로 스파이크가 사라져 넣지 않았습니다.

**효과:** 소환 직후 최대 프레임 301.5 → 34.4 ms.

### 4. 몬스터 시야는 플레이어만 본다

**문제:** 시야 감지가 아군·중립·적을 모두 감지하도록 설정되어 있었습니다.

- 몬스터 200마리가 서로를 감지하는 시야 질의가 약 4만 개(몬스터 수의 제곱) 생겼습니다.
- 질의는 프레임당 처리량이 정해져 있어 CPU 비용뿐 아니라 플레이어를 늦게 알아채는 원인도 됩니다.

**변경:** `AMonsterAIController::GetTeamAttitudeTowards`가 몬스터는 아군, 나머지 폰은 적으로 판정하고, 시야는 적만 감지합니다.

- 플레이어 여부(`IsPlayerControlled`)로 가르지 않았습니다. 플레이어 폰은 조종되기 전에 감지 대상으로 등록되기 때문입니다.
- 그 시점에 적이 아니면 질의가 아예 만들어지지 않습니다.

**함께 찾은 버그:** 측정 중에 몬스터 수가 216에서 204로 줄었습니다.

- 팀 판정은 "둘 다 PlayerState가 있으면 같은 편"이라, PlayerState가 없는 몬스터끼리는 적이었습니다.
- 그래서 드래곤의 브레스와 버그의 공격이 다른 몬스터를 죽이고 있었습니다.
- 몬스터의 공격 대상에서 다른 몬스터를 뺐습니다(`IsValidMonsterDamageTarget`).

### 5. StateTree 판단 주기 10Hz

**변경:** `STree_Bug`의 루트 상태에 Custom Tick Rate 0.1초를 두었습니다.

- StateTree의 예약 틱(scheduled tick)이 켜져 있어, 트리 전체(전역 태스크 포함)가 초당 10번 판단합니다.
- 이동은 경로 추종 컴포넌트가 매 프레임 따로 처리하므로 움직임은 끊기지 않습니다. 반응 지연은 최대 0.1초입니다.

**효과:** 바로 앞 단계를 다시 잰 값(23.7 ms)에서 교전 평균 21.9 ms로 줄었습니다. 플레이어를 쫓는 몬스터 수는 그대로였습니다(32 → 37).

### 6. 피격용 물리 바디 일괄 갱신

**문제:** 버그 메시에는 피격 판정용 물리 바디가 9개씩 있습니다. 캡슐이 움직이거나 자세가 바뀔 때마다 바디를 하나씩 옮기느라 프레임당 약 3 ms(트레이스 기준)를 썼습니다.

**변경:** 몬스터 메시에 `bDeferKinematicBoneUpdate`를 켜서, 물리 시작 전에 모든 몬스터의 바디를 한꺼번에 병렬로 옮깁니다.

- 서버의 플레이어 공격 검증 RPC는 프레임 시작(TickDispatch)에 처리됩니다.
- 그때 바디는 지난 프레임 끝 위치로 이미 맞춰져 있으므로 판정 정확도는 같습니다.

### 7. 졸개 복제 빈도

**변경:** `BP_Bug`의 `NetUpdateFrequency`를 기본 100Hz(서버 틱에 묶여 실제로는 30Hz)에서 10Hz로 낮췄습니다.

- 클라이언트는 위치 사이를 보간하므로 움직임은 부드럽게 보입니다.
- 드래곤은 30Hz를 유지합니다.

**효과:** 클라이언트 1명에게 보내는 양 47.8 → 23.9 KB/s. 보스 레이드 최대 인원 6명이면 서버 송신량도 그만큼 줄어듭니다.

### 8. 졸개 일제 사망

| 단계 | 10초 평균 | 최대 | 예산 초과 |
| --- | --- | --- | --- |
| 기준선 (서버도 래그돌) | 23.1 ms | 113.8 ms | 6프레임, 188 ms |
| 서버 래그돌 끔 | 7.1 ms | 95.6 ms | 2프레임, 67 ms |
| 시체 제거 시각 분산 (최종 3회 중앙값) | 5.9 ms | 77.2 ms | 1프레임, 44 ms |

**서버 래그돌 끔:**

- 래그돌은 화면마다 따로 시뮬레이션하고 복제하지 않습니다. 그런데도 전용 서버가 시체 200구의 래그돌을 8초 동안 돌리고 있었습니다.
- 전용 서버에서는 시뮬레이션하지 않고, 시체가 공격 판정을 가로막지 않게 충돌만 끕니다(`UCharacterDeathComponent::ApplyDeathPhysics`).

**시체 제거 시각 분산:**

- 한꺼번에 죽은 시체가 8초 뒤 같은 프레임에 사라지면서 60 ms 스파이크가 났습니다.
- 디졸브가 끝난 뒤 0~1초 사이로 흩어 지웁니다.

남은 1프레임은 200마리가 실제로 죽는 프레임입니다. 그 프레임의 비용은 다음과 같습니다.

- GAS 사망 효과 적용(200마리에 35 ms)
- 사망 복제
- 물리 바디 정리

### 9. 클라이언트

| 단계 | 교전 평균 | p95 | 게임 스레드 | 렌더 스레드 | GPU |
| --- | --- | --- | --- | --- | --- |
| 기준선 | 22.6 | 25.7 | 22.6 | 6.2 | 11.1 |
| 체력바·바디 일괄 갱신 | 21.5 | 28.1 | 21.5 | 6.8 | 11.3 |
| 화면 밖 이동 주기·URO | 14.7 | 17.1 | 14.6 | 6.9 | 8.9 |
| 최종 (2회) | 13.9 | 16.7 | 13.9 | 6.5 | 9.0 |

단위는 ms이고, 1280x720 창에서 플레이어가 드래곤을 바라보는 화면입니다. 병목은 처음부터 게임 스레드였습니다.

**화면 밖 몬스터의 이동 주기 낮추기:** 게임 스레드에서 가장 큰 비용(6.4 ms)은 복제받은 버그 200마리의 이동 시뮬레이션이었습니다. 매 프레임 캡슐 스윕과 바닥 검사를 합니다.

- [`UMonsterSignificanceSubsystem`](../Source/LabProject/AI/Monster/MonsterSignificanceSubsystem.h)이 0.2초마다 몬스터가 화면에 그려졌는지 봅니다.
- 화면 밖이면 이동 시뮬레이션을 0.25초마다(`pd.Monster.OffscreenMovementTickInterval`) 돌리고, 다시 보이면 매 프레임으로 돌립니다.
- 주기를 몬스터마다 조금씩 달리해 같은 프레임에 몰리지 않게 했습니다.
- 서버 위치는 계속 복제되고 판정은 서버가 하므로 게임 결과는 바뀌지 않습니다.

**URO:** 클라이언트에서도 몬스터 메시의 갱신 주기 최적화를 켜서, 멀리 작게 보이는 버그는 애니메이션을 몇 프레임에 한 번만 평가합니다.

**체력바:** 졸개는 피해를 입은 뒤에만 체력바를 보입니다(`bShowHealthBarAtFullHealth`). 화면에 보이는 버그마다 텍스트가 든 체력바 위젯을 그리던 Slate 비용이 약 1.2 ms 줄었습니다. 드래곤은 늘 보입니다.

**바디 일괄 갱신:** 6번의 일괄 갱신은 클라이언트에도 적용됩니다.

### 그 밖에 고친 것

- **`ABP_Baddy` 중복 슬롯:**
  - 메인 그래프와 걷기 상태 안에 `DefaultSlot` 노드가 하나씩 있었습니다.
  - 버그가 하나 생길 때마다 경고 로그를 남겼고, 소환 한 번에 212줄이 찍혔습니다.
  - 상태 안의 슬롯을 빼고 입력 자세를 출력에 바로 이었습니다. 몽타주는 메인 그래프의 슬롯에서 재생됩니다.

## 하지 않은 것과 다음 단계

- **NavWalking:**
  - 바닥 검사 대신 내비메시 투영을 쓰는 이동 모드입니다. 아낄 수 있는 시간이 1 ms 안팎입니다.
  - 넉백(낙하 전환)과 내비메시가 없는 클라이언트의 보간에서 부작용 위험이 있어 넣지 않았습니다.
- **사망 프레임:** 200마리가 같은 프레임에 죽는 비용(약 77 ms)이 남았습니다. 사망 처리를 큐에 넣어 몇 프레임에 나누면 줄일 수 있지만, 사망 판정 시각이 조금씩 달라집니다.
- **메시 LOD:** 버그 메시는 LOD가 하나(약 1.1만 삼각형)입니다. 지금 화면에서 GPU는 9 ms로 병목이 아닙니다. 해상도를 높이거나 저사양을 지원할 때 LOD를 만듭니다.
- **거리 기반 AI LOD:** 경기장이 좁아 모든 몬스터가 플레이어 가까이 있으므로, 거리로 판단 주기를 나누는 효과는 작습니다. 맵이 넓어지면 중요도 서브시스템에 거리 단계를 더합니다.
